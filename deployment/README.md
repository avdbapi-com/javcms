# JAVCMS server deployment profiles

Use the extracted package directory containing `index.php`, `api.php`, `javcms.php`, and `install.php` as the application document root. This application does **not** have a separate `public/` document root. Keep bundled `vendor`, `thinkphp`, `extend`, `static`, and `template` directories in place. Do not move PHP entry points, rename APIs, replace application routes, or require an asset build.

These are reviewed configuration examples, not an automatic installer for your panel. Back up the existing site configuration and `.htaccess`/`web.config` before applying them. Keep panel-generated certificate, logs, PHP pool/socket, ownership, and domain settings. Render examples into a fresh review directory with `render-profile.py`; it does not edit server configuration. The examples use a single application per vhost and a local PHP endpoint.

## PHP and installation

The entry-point minimum is PHP 7.4. PHP 7.4 through 8.5 have finite version-specific fixture/syntax coverage, including four genuine OPcache config-replacement assertions on each branch. Experimental PHP 8.6.0RC2 passed 58 focused runtime and 5 syntax checks; this is not full web-stack certification. There is no upper-version guard: later PHP 8.6+ or 9.0 can be attempted and tested when available, but their compatibility is not guaranteed. PHP before 7.4 is unsupported by this release. Use a maintained PHP version offered by your host rather than assuming the minimum is a maintenance recommendation; consult [PHP's supported-version lifecycle](https://www.php.net/supported-versions.php).

Enable PDO/`pdo_mysql`, XML, GD, mbstring, cURL, ZIP, and fileinfo. Create an empty MySQL/MariaDB database and a dedicated account before opening `/install.php`; the installer uses an existing database and does not replace tables with an occupied prefix. Set the PHP process's working directory to the application root if your handler does not already do so.

During installation, the PHP user needs directory write access to `application` for atomic configuration staging, and write access to `runtime`, `upload`, `application/extra`, `application/data/install`, `application/data/backup`, and `application/data/update`. It needs to create/replace `application/database.php`, `application/route.php`, and `application/extra/maccms.php`. The installer creates missing `runtime`, `upload` and `application/data/*` folders itself when the parent folder is writable, and shows each failed check in plain English with the permission fix. After installation, restrict general source-directory write access where your deployment permits, while retaining the specific configuration files/directories required for admin settings, routes, backups, and updates. Grant ownership/ACL permissions to the site PHP identity; do not use world-writable `777` or grant everyone Full Control.

Open `/install.php`, finish the environment and database checks, enter the site name and the public site URL (prefilled from the current address; an `https://` URL makes HTTPS the canonical protocol for canonical links and sitemaps), answer "Which catalogs will you import?" (AVDB / xvidapi / both / decide later: only the chosen seeded categories are enabled; with xvidapi the display name of the provider parent category, International or Western, slug `western` unchanged), then sign in at `/javcms.php`. The installer also creates the 1.2.0 tables (search index, scale counts, sitemap buckets, hit buffer, importer state) and the two list indexes on the empty video table, and records the result in `application/data/install/schema.json`. Keep `application/data/install/install.lock`. Public APIs/receiving services remain disabled until enabled deliberately in admin settings. No example in this directory enables them or supplies credentials. Preserve existing JW8 and advertisement configuration. A renamed admin entrance requires changing its literal name in every applicable server allowlist and its PATH_INFO rule.

## Subdirectory constraints

One-click updater (1.2.1) on a URL mount: the root `.htaccess` keeps update steps running on LiteSpeed while the maintenance page is on with `RewriteCond %{DOCUMENT_ROOT}/runtime/update/maintenance.php -f`; mod_rewrite has no variable for the folder of the `.htaccess`, so at `/cms` write `%{DOCUMENT_ROOT}/cms/runtime/update/maintenance.php` there (same line in `deployment/apache/root.htaccess` and `deployment/openlitespeed/root.htaccess`). The `?jcupd=` rule needs no change. Updates never replace a `.htaccess` (or `web.config`) the site changed: the release's new copy waits in `runtime/update/merge/<version>/htaccess.jcupd.txt` (`web.config.jcupd.txt`) and the Updates page names it; merge new lines such as these by hand.

Prefer `https://site.example/` with the app as that domain's root. A package filesystem subdirectory chosen as the domain's document root still has an **empty** URL prefix. A URL mount `https://site.example/cms/` is different: Apache/IIS rules match relative to app root; Nginx rendering requires `--prefix /cms`, `--web-root /srv/site`, `--app-root /srv/site/cms`. Do not use Nginx `alias` with these profiles. Keep it out of another app's catch-all rules, and adapt both HTTP/HTTPS frontend protections. The application site path/base URL must be configured for `/cms`; root-relative URLs in existing themes, players or third-party integrations may need independent verification. Server rewrite checks do not certify every theme at a subdirectory URL.

Example review render:

```sh
python deployment/render-profile.py --app-root /srv/javcms --web-root /srv/javcms --php-endpoint unix:/run/php/site.sock --output /srv/private/javcms-render
```

The deployment directory itself is HTTP-denied. The Nginx include paths refer to filesystem files and remain usable by the server. Keep examples and private review output out of public backup locations. Existing public `static`, `template` assets, upload images/video/subtitles, `robots.txt`, and sitemaps are not globally denied. The guards deny private roots, dotfiles except ACME challenges, configuration/database dumps, root archives, executable uploads and PHP scripts other than the four entrances.

## robots.txt

The package ships no static `robots.txt`. `/robots.txt` is generated by `application/index/controller/Robots.php`: the crawl rules plus a `Sitemap:` line for the configured site domain, scheme and URL mode. Every profile above routes `/robots.txt` to `index.php` explicitly, and the generic front-controller fallback of any panel does the same. For custom crawl rules, create a root `robots.txt`: the profiles still pass it through the application, which keeps your rules and replaces only the Sitemap line of this site (a panel rewrite without the explicit rule serves the file as it is). Expected check: `/robots.txt` answers 200 `text/plain` with `Sitemap: https://<your domain>/sitemap.xml`.

## Visitor theme switcher and HTTP caches

Admin, Site & theme > Themes, card "Visitor theme switcher" (the release package ships it turned on: `site.theme_switcher` = `'1'` in `application/extra/maccms.php`; a missing key means off): where the button shows (`site.theme_switcher_show`: `always`, the default, which a missing key also means, is a floating button on every screen; `header` is an icon next to the theme's light/dark button, with the floating button wherever the header has no room for it or has scrolled out of view; `end` shows the button only at the end of the page, the 1.2.0 behaviour), the corner of the floating button, and an optional list of offered themes. Site identity shows a status line only, and its save never changes these settings. The card's save is refused with a request to reload the page when it would undo switcher settings saved after the page was opened (another tab or another admin); saving the same settings again, for example after a lost connection, simply works. `php tools/upgrade.php` adds `site.theme_switcher_show` = `always` when the key is missing and never changes a stored value. When an update is copied by hand in parts, copy `static/` before `application/` (or everything in one go): a page of the new PHP files with the old switcher script keeps the header icon hidden and uses the floating button until the new script is there. "Website template" stays the default for first visits. New theme folders are offered to visitors only after the settings are saved again. With a separate mobile template, phones get that template as their default and can still pick the desktop one. The server re-sends `jv_theme` only on HTML pages that show the switcher, never on `robots.txt`, sitemaps, feeds or JSON answers. On a sub-directory install the cookie path is that directory. The visitor's choice is the cookie `jv_theme` (a theme folder name, validated against the offered list on every request; never a path), mirrored in `localStorage['javcms.theme']`.

Since 1.2.0, HTML that is the same for every anonymous visitor (no session, member, theme-choice or ad-preview cookie; the language cookie only when it names an enabled locale) is sent with `Cache-Control: public, max-age=0, s-maxage=300` and `Vary: Accept-Encoding`, without `Set-Cookie`; every other response keeps `Cache-Control: no-store` plus `CDN-Cache-Control` / `Cloudflare-CDN-Cache-Control: no-store`. With a separate mobile template, `s-maxage=0` is sent (a CDN cannot vary by user agent). Use the Cloudflare Cache Rule shown in Admin, Speed & protection (it bypasses the admin entrance, `/api.php`, `/user`, `/ajax`, `/jcx` and the cookies `user_id`, `PHPSESSID`, `avdb_ui_lang`, `jv_theme`, `jcxp`). If you put another caching proxy in front (Varnish, an Nginx `proxy_cache`, a "cache everything" rule), honour `s-maxage`/`no-store` or add the cookies `jv_theme`, `jv_theme_preview` and `avdb_ui_lang` to its cache key, otherwise one visitor's theme or language is served to others. Static pages (Admin, URL settings, mode "static HTML") are rendered once for everybody and ignore the visitor's choice; the switcher card on the Themes page warns when such a mode is on.

## 1.2.0: page cache, request limits, cron and large catalogs

**Page cache and locks.** `index.php` serves cached anonymous pages from `runtime/edge/` before the framework starts, and the request gates use lock files under `runtime/`. Keep `runtime/` on a local disk where `flock()` works: on NFS or some FUSE/CageFS mounts the gates fail open and Admin, Speed & protection shows "File locks are not supported here". The cache has size caps (256 MB / 20,000 files up to 1 GB / 100,000 files by catalog size), so it cannot fill the disk.

**Visitor address behind a proxy.** Per-network budgets (default 300 heavy and 2,400 light uncached requests per minute per IPv4 address or IPv6 /64, `app.budget_heavy` / `app.budget_light`, adjustable on Speed & protection; Under attack mode `app.under_attack` lowers them to `app.attack_budget_heavy` / `app.attack_budget_light`, default 30 / 240; verified search-engine crawlers are exempt in both modes) need the real visitor address. When PHP sees a loopback, private or link-local peer (Nginx in front of Apache/OLS, a panel proxy, a load balancer, cloudflared) and no trusted proxy is configured, the budgets are off for that peer and Speed & protection shows "All visitors appear to come from <ip>". "Trust this proxy" there writes `application/extra/public_request_guard.php` (`trusted_proxies`, `proxy_header`); only a loopback/private/link-local peer can be trusted. Preserve the proxy's forwarded headers. With Cloudflare Tunnel, use the Tunnel switch instead (trusts `CF-Connecting-IP` from 127.0.0.1/::1). Behind Cloudflare without a tunnel, `CF-Connecting-IP` is trusted only from Cloudflare's published ranges.

**Origin lock.** After Cloudflare is on, allow ports 80/443 only from Cloudflare's ranges (Speed & protection prints ufw, Apache `Require ip` and Nginx `allow` snippets with the current list), change the server address and do not send mail from it. See `docs/SECURITY.md`.

**Cron.** Recommended every 5 minutes (faster imports, maintenance; sites above about 1,000,000 videos should have it); imports of any size also run without cron from the admin page. Use the same PHP version as the site (7.4+):

```
*/5 * * * * php /path/to/site/tools/import.php --run --max-minutes=4 >/dev/null 2>&1
*/5 * * * * php /path/to/site/tools/housekeeping.php >/dev/null 2>&1
```

Panel PHP binaries are often `/usr/local/bin/ea-php74` (cPanel EasyApache), `/opt/alt/php74/usr/bin/php` (CloudLinux), `/usr/local/php74/bin/php` (DirectAdmin) or chosen in the Plesk task form. Every CLI tool refuses the web SAPI and PHP < 7.4, runs at low priority (`proc_nice(19)`) and prints no credentials. After an upgrade, `php tools/upgrade.php` adds the two list indexes (or use "Finish upgrade" in the admin; both also build the sitemap files right away, as the installer does, once the sitemap blocks exist, refresh the search index's word statistics and term map when they are due (an index built by an earlier 1.2.0 build, more than 5 % new videos, older than a week; "Finish upgrade" leaves a term map that does not fit into its minute to housekeeping with cron or PHP-FPM), and download the search engines' current IP lists) and `php tools/search-index.php --backfill` fills the search index. Without either of them, refresh the word statistics of an earlier 1.2.0 search index once with `php tools/search-index.php --terms` and then `php tools/search-index.php --map`; housekeeping and its cron line never refresh them. Packagers run `php tools/housekeeping.php --write-crawler-lists` right before building a release package: it refreshes `application/data/crawlers/*.json`, the search-engine IP lists the package ships (exit code 0 = all four written).

**Database server for large catalogs.** For 2-7 million videos use MariaDB 10.6+ or MySQL 8.0 with `innodb_buffer_pool_size` 1-1.5 GB (512 MB works with less headroom) and about 8 PHP-FPM workers. On MySQL 8, a single server without replication should switch the binary logs off (`skip-log-bin`) before the first big import, or set `binlog_expire_logs_seconds=86400` and leave room for them: a full xvidapi import with real rows writes about 52 GB of binary logs in MySQL 8's row format (MariaDB with binary logs on: about 41 GB mixed, about 89 GB row format with row annotations; the import estimate reads `@@binlog_format`), and with the 1-day setting those of a running import stay until a day later. The search index needs MySQL 5.7+ or MariaDB 10.2+; older engines use the fallback search. Sizes per catalog: `docs/HOSTING.md`.

## Required HTTP checks after applying a profile

Check the real host after its configuration test: `/install.php` (new installs), `/javcms.php`, `/javcms.php/admin/index/login`, `/javcms.php/admin/index/captcha`, `/api.php/provide/vod/?ac=list`, `/api.php?s=provide/vod&ac=list`, an existing `/detail/...` and `/play/...`, public map/rss/sitemap routes, one `/static/...js` and CSS/font asset, one `/template/jav/...` asset and one known public upload. Disabled APIs should return the application's documented disabled response, not a server 404 or PHP source. The canonical captcha path includes the `admin` module; omitting it can lead to the login page.

Static SVG (the auto-icon sprites under `static/template-ui/auto-icon/`) must arrive compressed: `curl --compressed -D - -o NUL <site>/static/template-ui/auto-icon/sprite-lucide.svg` shows `Content-Encoding: br` or `gzip`.

Private probes must be denied before PHP or static delivery: `/application/database.php`, `/runtime/index.html`, `/vendor/composer/installed.json`, `/thinkphp/start.php`, `/extend/`, `/deployment/README.md`, `/.git/config`, `/upload/test.php`, `/upload/test.php.jpg`, and an unknown root PHP file. Use disposable private fixture files for execution tests; never upload a public test shell to production. Verify query strings, methods and bodies with a harmless transport fixture, then remove it. Ensure guards work via the frontend as well as any direct backend. Check logs for warnings, asset 404s, and unintended redirects; check server reload/rebuild retains custom rules.

On IIS, if a bundled asset returns 404.3, inspect MIME mappings before changing route rules. Add missing `.json` (`application/json`), `.woff2` (`font/woff2`), `.woff` (`font/woff`), `.wasm` (`application/wasm`), `.webm` (`video/webm`), `.vtt` (`text/vtt`), `.m3u8` (`application/vnd.apple.mpegurl`) and `.ts` (`video/mp2t`) types through site MIME Types. Do not add a duplicate mapping or permit PHP source as static content. Inspect actual player requirements for subtitle/stream formats.

Official references and the finite verification status are in `sources.json` and `verification-status.json`. Apache's `B` flag and IIS URL Rewrite's `UrlEncode` function escape decoded route backreferences before adding them to the compatibility query parameter; this preserves encoded `&` and `#` in route paths. The finite checks distinguish harmless transport/installer probes from a complete application install. No static check alone establishes panel runtime compatibility.
